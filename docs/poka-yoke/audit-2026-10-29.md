# Ovanite production-readiness audit — 2026-10-29

## Scope and verdict

Read-only review of the current `main` source and repository history, security-sensitive backend APIs, frontend release gates, Vercel public routes, CI workflows, deployment configuration, and all pull requests found in the repository history available to the connected GitHub account.

**Verdict: not production-ready for a live backend-powered service.** The public marketing frontend is available, but backend identity, backend deployment, object storage, owner provisioning, and the separately deployed participant portal still have release blockers. Keep administrator writes, public Contact/Waitlist submissions, analytics writes, and participant intake closed until their individual gates pass.

## Public deployment smoke check

On 2026-10-29, the following canonical public URLs each returned HTTP 200: [home](https://ovanite.vercel.app/), [runtime config](https://ovanite.vercel.app/env.json), [identity diagnostic](https://ovanite.vercel.app/identity-check), [admin](https://ovanite.vercel.app/admin), [contact](https://ovanite.vercel.app/contact), [waitlist](https://ovanite.vercel.app/waitlist), [participants](https://ovanite.vercel.app/participants), and [participants submission route](https://ovanite.vercel.app/participants/submit).

The routes consistently identify Ovanite. The admin route is gated; Contact and Waitlist display that collection is disabled; the participant submission URL renders an overview only and contains no submission fields. The identity diagnostic is served on the canonical origin but sign-in was not attempted. The public `/env.json` reports `backend_host=https://icp-api.io` and still reports `undefined` for backend canister ID, project ID, Internet Identity derivation origin, and storage gateway URL. HTTP 200 is not evidence that backend operations work.

## Findings ranked by release impact

### 1. Production backend has not been deployed — release blocker

**Mistake:** treat a successful Vercel frontend deployment or a local ICP test as a production backend deployment.

**Consequence:** normal actor calls have no verified canister target; owner/admin operations and persistence cannot be proven live.

**Current control:** runtime configuration fails closed when no verified backend ID is set; CI builds and tests a disposable local canister. No mainnet canister ID is recorded and no mainnet cycles were spent.

**Required control:** deploy the backend independently using a verified controller identity and approved cycles budget, record the real canister ID, verify controller/cycles/status, compare the deployed Candid interface with the generated bindings, configure Vercel, and run production API smoke tests.

### 2. Public analytics write abuse — mitigation in this change

**Mistake:** assume the browser consent banner protects the public `recordPageView` canister update.

**Consequence:** a direct caller can bypass UI consent, supply unbounded distinct route keys within the length limit, grow persistent state, poison aggregate counts, and repeatedly consume canister cycles.

**Previous control:** frontend consent and route normalization only; no server-side write release gate.

**Device:** `src/backend/lib/analytics-policy.mo` disables public analytics updates at the Motoko boundary, independent of caller. A PocketIC regression test checks that anonymous and signed-in calls fail without creating route rows. Re-enable only after finite route cardinality and effective ingress abuse/cost controls are validated.

### 3. Caffeine-specific object storage is unverified — release blocker

**Mistake:** point the exported object-storage adapter at a guessed or merely syntactically valid URL.

**Consequence:** images or blobs may fail, data may be inaccessible, or a backend may expose broken storage behavior.

**Current control:** deployment documentation explicitly flags the adapter and does not invent `storage_gateway_url`.

**Required control:** prove upload/read/delete against a documented independent storage endpoint or replace the adapter and test it. Verify access isolation and size/type limits before enabling image uploads.

### 4. Owner provisioning deliberately has no principal — release blocker for admin use

**Mistake:** substitute an email address, Caffeine project UUID, preview-origin principal, or guessed identifier for the final canonical-origin Internet Identity principal.

**Consequence:** owner lockout or unauthorized ownership if the guard were weakened.

**Current control:** `ownerPrincipalText = null`; bootstrap rejects while unconfigured; negative-path tests cover anonymous, unconfigured, and repeated claims. The `/identity-check` diagnostic is available on `https://ovanite.vercel.app` but has not been used by the owner in this audit.

**Required control:** the operator signs in on the canonical production origin, reads the public principal locally, then uses a reviewed source change and verified backend redeployment. Never transfer a passkey, seed phrase, recovery phrase, private key, token, or delegation.

### 5. Contact/Waitlist writes remain disabled — intentional release gate

**Mistake:** enable personal-data collection just because a page is reachable or the backend health check works.

**Consequence:** sensitive data could be lost, spammed, retained without an operating process, or accepted without effective abuse controls.

**Current control:** frontend release flag is default-false and backend Motoko policy rejects direct writes. Payloads are bounded and duplicate receipts are redacted.

**Required control:** validate persistent storage, deduplication, abuse/rate controls, privacy notice/retention/deletion, support response, monitoring, and end-to-end tests. Then separately approve the frontend flag and reviewed backend policy change.

### 6. Participant portal is not operationally released — release blocker for intake

**Mistake:** present the integrated overview or static security scan as a functioning submission and evaluation service.

**Consequence:** participants may submit into a path with no verified database, login callback, reviewer isolation, or durable lifecycle.

**Current control:** intake is closed; the page has no live form. Portal code has typecheck/test/build/Trivy/actionlint gates and a static-only scan workflow; it does not execute candidate code.

**Required control:** deploy the separate portal, configure OAuth/callback secrets and database connection privately, review and apply additive migration `0002`, test roles/ownership and callback round-trips, set limits/monitoring, and test lifecycle/evaluation end to end. Keep arbitrary candidate code execution out of the static worker.

### 7. CI proof is strong but not a live release — operational gap

**Mistake:** infer that passing lint/build/local-network checks establish live identity, storage, ownership, or production cycles.

**Consequence:** hidden integration failures remain until users reach the application.

**Current control:** pinned tool versions, lockfile validation, frontend typecheck/lint/unit/build checks, Motoko checks/stable-state compatibility, disposable local ICP deployment, and authorization regressions.

**Required control:** after the separate backend and portal deployments, run production smoke checks on the exact live domains and record immutable commit/deployment identifiers and results. Vercel connector access to project settings/deployment details was denied in this audit; no Vercel environment variables or deployment settings were changed.

## Release decision

**Do not announce a production launch for backend-powered functionality yet.** The static marketing site is publicly reachable, but this audit did not deploy a mainnet canister, spend cycles, sign in as the operator, change Vercel settings, configure production secrets, apply the participant portal migration, or enable any intake. ### Launch verdict
**Ovanite is not yet production-ready for data-taking workflows.** The public marketing frontend is reachable, but its current production deployment is behind main and the backend has no verified live canister. Participant intake, Contact/Waitlist persistence, analytics writes, and owner/admin operations must remain disabled until the actual backend/provider is provisioned, owner identity and storage are verified, migrations and authorization are tested on an isolated deployment, and end-to-end smoke tests pass against the final production origin. This re-audit does not claim that a launch or production backend deployment occurred.

### Release decision
