# Ovanite backend deployment audit

Last verified: 2026-10-29.

## Verified deployment state

Ovanite's public React/Vite frontend is hosted at https://ovanite.vercel.app. The site was exported from Caffeine and its Motoko backend has **not** been deployed independently to the Internet Computer mainnet.

The public runtime configuration at https://ovanite.vercel.app/env.json currently reports:

```json
{
  "backend_host": "https://icp-api.io",
  "backend_canister_id": "undefined",
  "project_id": "undefined",
  "ii_derivation_origin": "undefined",
  "storage_gateway_url": "undefined"
}
```

The `backend_host` value is generated by the Vercel production build's default. A canister ID, Caffeine project ID, identity derivation origin, or storage gateway must not be invented to replace the unresolved values. The project owner has reported that Vercel's Environment Variables page is empty. The Vercel connector used during the audit did not have access to the Ovanite project, so it could not modify or independently inspect the project settings.

A committed Motoko source file, generated WASM/Candid files, or a successful Vercel frontend deployment do not prove a production backend canister exists or works.

## Backend verification

The repository has an independent ICP CLI manifest at `icp.yaml` declaring the Motoko `backend` canister. The backend-quality workflow uses pinned Mops and ICP CLI versions, checks the locked dependencies, type/lint/stable-state compatibility, builds with Mops and the ICP CLI, verifies generated WASM/Candid artifacts, and deploys the canister to a disposable **local** ICP network.

These checks are local/CI validation only. They do not create a mainnet canister, prove that an independent storage gateway exists, or prove the frontend talks to a production canister.

## Runtime configuration

The Vercel runtime-config generator is already implemented in `src/frontend/scripts/generate-runtime-config.mjs`; the canister ID mapping is implemented in `src/frontend/scripts/backend-canister-env.mjs`. The deployed build defaults `backend_host` to `https://icp-api.io`, validates HTTPS URLs and canonical IC principal syntax, and keeps an unconfigured backend ID as `undefined`. It maps a verified `OVANITE_BACKEND_CANISTER_ID` into the generated public runtime config and the actor SDK's `CANISTER_ID_BACKEND` setting.

A syntactically valid principal is not evidence that a canister exists, has the expected Candid interface, has enough cycles, or is reachable. Do not set `OVANITE_BACKEND_CANISTER_ID` until an independent deployment has returned the real ID and the deployed interface has been checked.

All values written to `env.json` are public and must never contain passwords, private keys, API tokens, identity recovery material, or any other secret. Relevant optional variables:
- `OVANITE_BACKEND_HOST`: an HTTPS origin; production defaults to `https://icp-api.io`.
- `OVANITE_BACKEND_CANISTER_ID`: canonical ID of the verified deployed backend; required before backend methods can work.
- `OVANITE_II_DERIVATION_ORIGIN`: leave unset until the identity-origin design is verified.
- `OVANITE_CAFFEINE_PROJECT_ID`: Caffeine-specific, not a canister ID; do not set merely because the former Caffeine project UUID is known.
- `OVANITE_STORAGE_GATEWAY_URL`: leave unset until the independently deployed storage integration is proven.
- `OVANITE_PUBLIC_FORMS_ENABLED`: defaults to closed; do not set to `true` until all relevant persistence, privacy, abuse-control and end-to-end checks pass.

## Security posture

- `src/backend/lib/admin.mo` deliberately keeps `ownerPrincipalText = null`. Owner bootstrap is disabled until the exact operator principal for Ovanite's final identity origin has been verified and configured in a reviewed backend change. Never use an email address or Caffeine project ID as identity proof.
- `src/backend/lib/submission-policy.mo` separately disables direct Contact/Waitlist writes. The frontend form flag cannot override this backend authorization gate. Both public forms currently render no personal-data fields.
- `src/backend/lib/analytics-policy.mo` now disables public page-view updates at the Motoko boundary. The frontend consent banner cannot stop direct canister calls; before this gate, arbitrary distinct paths could grow persistent analytics state and repeated calls could consume cycles. Do not enable analytics writes until route cardinality and ingress abuse/cost controls are implemented and tested.
- `/participants/submit` remains an overview-only route; participant intake must stay closed.
- Backend and frontend source still reference Caffeine-specific object-storage packages. An independently compatible gateway has not been proven. Image upload/download remains blocked until upload, read, and delete tests pass against a verified storage implementation or the adapter is replaced.
- No mainnet canister was deployed and no mainnet cycles were spent during this audit.

## Additional abuse-control release gate

- Public analytics writes are now disabled by a server-side Motoko release policy, independent of browser consent. Re-enable only after choosing a finite canonical route vocabulary and verifying ingress-level rate/cost protections; anonymous client-side consent alone is not a security boundary. The current behavior deliberately favors bounded operational risk over live page-view counting.

## Required release gates

1. Verify that `https://ovanite.vercel.app/identity-check` is served by the current production deployment. A successful Vercel status check alone does not prove the custom-domain alias is already serving the route.
2. On that canonical production origin, the operator must sign in with their own Internet Identity and read the public principal from the diagnostic page. Do not ask for or transmit a passkey, seed phrase, recovery phrase, private key, authentication token, or delegation. Do not reuse a principal from a preview or alternate origin.
3. Review and resolve Caffeine object-storage dependencies for independent hosting. Prove upload/read/delete using a verified endpoint, or replace the adapter with a documented and tested alternative. Never guess `storage_gateway_url`.
4. Confirm the mainnet architecture and cycle budget. ICP mainnet canisters consume cycles for compute and storage; local pre-funded development does not establish free production operation. Explicitly approve funding and ongoing costs before mainnet deployment. References: https://docs.internetcomputer.org/concepts/cycles/ and https://cli.internetcomputer.org/1.7/guides/deploying-to-mainnet/.
5. Build and deploy the backend to mainnet using the confirmed deployment identity and funded cycle balance. Capture the actual backend canister ID, check its controller and cycle status, and verify that its deployed Candid interface matches the generated frontend bindings.
6. Configure Vercel with the verified backend ID. Use the generated runtime-config contract; do not hardcode or commit a guess into `env.json`. Confirm the production `/env.json` advertises the exact deployed canister ID.
7. Configure `ownerPrincipalText` to the verified principal in a reviewed backend change; rebuild and deploy. Prove the configured owner succeeds while anonymous, wrong-principal, and repeated claims fail.
8. Test admin CRUD, owner-only team changes, authorization boundaries, data isolation, upgrade/migration compatibility, public data reads, and storage operations against local/staging and production canisters.
9. Keep Contact/Waitlist disabled until persistence, deduplication, rate/abuse controls, privacy/retention, operational support, and end-to-end checks pass. The frontend flag is not authorization.
10. Keep participant intake closed until the separate participant portal has verified identity, database persistence, data ownership, reviewer permissions, migrations, rate limits, callback credentials, privacy controls, and end-to-end tests.
11. After deployment, record verifiable evidence for the commit, production URL, backend canister ID, deployed Candid, canister status/cycles, identity origin, storage test results, and security tests.

**Do not treat a successful frontend deployment or a local canister build as proof of a functioning production backend.**
